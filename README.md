# Biological Constraints

Biological Constraints is a collection of 22 frozen, model-independent measurements of biological knowledge in DNA, RNA, protein-sequence and protein-structure foundation models. Each Constraint defines a biological relation, a ready-to-use reference set, a representation interface, a public scoring method and one or more conventional comparators. The paper implementations apply the same public scorers to five foundation models per biological domain.

This release is organized around three public directories:

- [`constraints/`](constraints/) — Constraint documentation, formal reference sets, public scorers and comparators;
- [`paper_cases/`](paper_cases/) — model resources, Forward implementations, scorer handoffs and registered paper results;
- [`analysis_and_visualization/`](analysis_and_visualization/) — the retained Figure 4c statistical analysis and all R-generated paper-figure assets.

The analysis directory contains the three formal tests shown in Figure 4c, with their input table, code, results and null draws. The figure directory contains  R-generated PDF subfigures with their plotting code and data; it is not a complete archive of manuscript artwork.

There is no separate `docs/` tree. This README explains the repository-wide workflows. Each Constraint README is the authoritative operational guide for that measurement.

## Start here

### Score a new model

Use this path when the model is not one of the paper models.

1. Select a Constraint from the 22-entry table below and open its `README.md`.
2. Read its **Forward/representation contract**: the scorer may require whole-object vectors, position-level vectors, residue-level vectors, paired views or another declared representation.
3. Encode every required RefSet object with the new model and export the exact IDs and arrays required by that Constraint.
4. Record the model/checkpoint, tokenizer, layer, windowing, coordinate mapping and pooling configuration required to interpret the result.
5. Run the exact command documented in the Constraint's `scoring/` section.
6. Keep the full scorer output: ID-level measurements or credits, aggregate result, confidence interval, coverage, hashes and output manifest.

```text
formal RefSet objects and relations
               +
new-model Forward outputs
               ↓
schema, ID-coverage and numeric validation
               ↓
frozen relation measurement and aggregation
               ↓
ID-level evidence + F + CI + coverage
```

The public scorer does not load the user's model. Tokenization, special-token removal, windowing, overlap handling and pooling belong to the model Forward. The scorer receives only the declared Forward output and applies the frozen measurement.

Do not copy a Paper Case result and replace its model name. A new result must be generated from that model's own Forward outputs through the Constraint-owned public scorer.

### Reproduce a paper result

Two reproduction levels are supported.

**Score-level reproduction** starts from a Forward output and reruns the public scorer. Large Forward representations are not necessarily distributed in this release; when they are absent, regenerate them with the case's Forward implementation before running the scorer:

1. Select the model × Constraint row in [`paper_cases/CASE_INDEX.tsv`](paper_cases/CASE_INDEX.tsv) and open its `result_path`.
2. Open the corresponding model directory and its `scoring_call/` documentation for the public-scorer invocation when that material is included.
3. Confirm the scorer-input binding, RefSet release and required representation files.
4. Run the command and compare the generated result with the files actually published under `models/<model_id>/output/`. The run generates any unpublished manifest or intermediate evidence.

**Full Forward reproduction** starts from the original checkpoint:

1. Read `paper_cases/model_resources/<domain>/<model_id>/` for the upstream source, checkpoint identity and executed software environment.
2. Follow `paper_cases/<domain>/<constraint_id>/models/<model_id>/forward/README.md` or `forward/IMPLEMENTATION.md` from the repository root.
3. Generate the formal Forward output with the documented tokenizer, layer, windowing and pooling method.
4. Run the case-specific command in `scoring_call/`.
5. Compare the generated result and evidence with the files published for that case and the registered result identified by the repository-level case index. ID-level outputs, manifests and other intermediates absent from the published case are generated by the reproduction run.

```text
formal RefSet + registered checkpoint
                ↓
paper-case Forward implementation
                ↓
formal representation artifact
                ↓
Constraint-owned public scorer
                ↓
registered paper result, ID-level output and output manifest
```

Weights are obtained from their original publishers. When the executed run used a local checkpoint file, its recorded SHA256 identifies the actual asset; a similarly named checkpoint is not automatically equivalent.

## What a Biological Constraint measures

A Biological Constraint is a frozen relation among biological objects together with a model-independent evaluation rule. A model supplies representations, predictions or readout inputs in the published format. The Constraint measures whether those outputs preserve a relation already fixed by sequence, structure, the genetic code, curated experimental evidence or another explicitly defined biological source.

The separation of responsibilities is strict:

```text
biological definition + RefSet + scoring method
                    owned by constraints/
                              ↑
model checkpoint + tokenizer + Forward + representation output
                    owned by paper_cases/ or the user
```

`paper_cases/` may call a scorer from `constraints/`; a Constraint never depends on a paper model. Comparator measurements also enter the Constraint-owned scoring path rather than defining a second scoring method.

## Repository structure

### Public Constraints

Each active Constraint is self-contained:

```text
constraints/<domain>/<constraint_id>/
├── README.md          # input contract, command, outputs and interpretation
├── refset/            # formal objects, relations, folds and dependency units
├── scoring/           # public numerical implementation and environment
└── comparators/       # conventional reference methods and registered results
```

The Constraint README is the operational starting point. Together with the released `refset/` and `scoring/` materials, it specifies the biological definition, representation unit, accepted input format, scorer command, output files, aggregation, uncertainty and score interpretation. Comparator implementations and results are kept under `comparators/`.

```text
paper_cases/<domain>/<constraint_id>/
├── README.md
└── models/<model_id>/
    ├── README.md
    ├── forward/                 # model-specific representation extraction
```

Not every case exposes every optional validation or binding artifact. The repository-level [`paper_cases/CASE_INDEX.tsv`](paper_cases/CASE_INDEX.tsv) is the complete navigation table for all 110 registered results and points directly to each current result file. Constraint-local indexes, where present, are supplementary records rather than required navigation files.

## Preparing Forward outputs for a new model

The Constraint README defines the exact schema. Common forms include:

- `object_ids` plus one whole-object vector per sequence or structure;
- sequence hashes, biological positions and position-level vectors;
- canonical residue IDs plus residue representations;
- separate representations for declared views or repeated calibration Forward passes;
- model-independent measurement ledgers produced from validated representations.

Before scoring, verify:

- every required formal object ID is present exactly once;
- no unexpected object IDs are included unless the README permits them;
- vectors have consistent dimensions and contain finite real values;
- sequence or structure identity fields refer to the released RefSet;
- nucleotide/residue mappings exclude special tokens and correctly handle k-mers, subwords, padding, truncation and overlapping windows;
- repeated Forward files are independently executed when the Constraint uses them for numerical calibration.

For position-level Constraints, a token index must not be assumed to equal a biological coordinate. The model owner must preserve enough evidence to reconstruct the token-to-nucleotide or token-to-residue mapping. The public scorer validates formal IDs and numeric inputs; it does not load or reinterpret a third-party tokenizer.

## Running a public scorer

There is no single repository-wide scoring command because each biological relation has its own inputs. The exact command is always located under:

```text
constraints/<domain>/<constraint_id>/README.md
constraints/<domain>/<constraint_id>/scoring/README.md
```

Run commands from the repository root unless the relevant README explicitly says otherwise. Use the component-specific environment in `scoring/ENVIRONMENT.md`. Do not run a model Forward environment as the scorer environment unless the documentation explicitly combines them.

A valid scoring release normally retains two output levels:

1. an ID-addressable ledger containing the raw measurements, formal credit or prediction, grouping identities and scorable status;
2. an aggregate result containing the primary score, confidence interval, coverage, method/RefSet identity and output hashes.

Cross-fit Constraints additionally retain held-out predictions or scores. Comparator and foundation-model outputs must be traceable to the same formal evaluation IDs when the Constraint defines such a comparison.

## RefSets and biological-coordinate mapping

RefSets are formal scientific inputs, not templates to redesign during scoring. They may contain:

- canonical sequence or structure objects;
- positive, negative, edit, variant, contact or transformation relations;
- parent, family, topology, source or dependency identities;
- cross-validation folds or calibration controls;
- nucleotide-, residue- or structure-coordinate mappings;
- formal population and coverage identities.

Routine evaluation uses the released RefSet. RefSet construction and materialization are separate from the scoring interface and are not required to score a model.

## Score and uncertainty semantics

The exact estimator is Constraint-specific:

- `F` is the reported formal score for all 22 Constraints;
- its mathematical definition, aggregation hierarchy and interpretation are specified by the owning Constraint;
- the 95% confidence interval uses the frozen dependency or bootstrap unit;
- coverage reports which planned formal units were successfully scored;
- ties, zero vectors, missing values and out-of-scope objects follow the Constraint-specific rule;
- a comparator score is a reference measurement on the same formal relation universe and is not necessarily a random-chance baseline.

Do not infer a universal chance level, tie tolerance or aggregation hierarchy from another Constraint. Interpret every result together with its Constraint release, formal population, representation interface, coverage and comparator class.

## Environments

The repository intentionally has no project-wide Python environment.

- Public scorer dependencies: `constraints/<domain>/<constraint_id>/scoring/ENVIRONMENT.md`
- Comparator dependencies: the relevant method under `constraints/<domain>/<constraint_id>/comparators/`
- Shared model dependencies: `paper_cases/model_resources/<domain>/<model_id>/ENVIRONMENT.md` and `ENVIRONMENT.json`
- Model × Constraint additions: the case-specific `forward/README.md` or `forward/IMPLEMENTATION.md`

Scoring environments are kept separate from large CUDA/model environments. Install only the component needed for the task being run.

## Result reporting checklist

When reporting a new result, include:

- Constraint ID and release version;
- model and checkpoint identity;
- representation layer, readout and pooling;
- tokenizer and biological-coordinate mapping where applicable;
- windowing, overlap and long-input handling;
- formal `F`;
- 95% confidence interval and coverage;
- scorer and RefSet identity;
- retained ID-level output and output manifest.

Model scores are measurements of specific biological relations. They are not a universal ranking of model quality and should not be averaged across Constraints without an explicitly defined cross-constraint analysis.
